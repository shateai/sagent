# Security Specification for Wealth Planner AI Agent

This document defines the security parameters, data invariants, and adversarial test scenarios for the Firestore database of the AI Wealth Planner application.

## 1. Data Invariants

1. **Agent Status (`agent_status/main`)**:
   - Primary state record represents the simulation metrics (accumulated capital, current strategy, agent state).
   - This document is **read-only** to authenticated clients (`auth != null` with email verified).
   - Direct writes or edits to `agent_status/main` from client SDKs are strictly **blocked/forbidden**. All updates must occur via server-side secure endpoints.
   
2. **Wealth Plans (`wealth_plans/{planId}`)**:
   - Hourly strategical plans generated by the server-side cron simulation logic.
   - Any authenticated, email-verified user can list/get wealth plans (`auth != null && auth.token.email_verified == true`).
   - Clients are strictly **forbidden** from creating (`create`), updating (`update`), or deleting (`delete`) plans. This prevents injecting fake "get rich" logs or bypassing simulation states.

3. **User Messages (`user_messages/{messageId}`)**:
   - Chat logs between individual users and the Gemini Advisory Assistant.
   - Users must only be allowed to access (read, query, create) messages that they themselves have created, or that belong to their specific session context. To achieve complete tenant separation and prevent PII leakage:
     - Messages will include an `ownerId` which must match the logged-in user's UID (`request.auth.uid`).
     - Standard reads/lists must enforce `resource.data.ownerId == request.auth.uid`.
     - Users can create messages where `incoming().ownerId == request.auth.uid`.
     - Users cannot update or delete messages once generated. Keep message history immutable.

## 2. The "Dirty Dozen" Adversarial Payloads (Red Team Test Cases)

Below are the 12 malicious payloads designed to exploit update gaps, identity spoofing, value poisoning, and orphan records. All of these attacks must result in `PERMISSION_DENIED` on the client.

### Case 1: Client Spoofing Capital in Agent Status (Value Poisoning)
- **Target**: `setDoc(doc(db, "agent_status", "main"), { status: "planning", capital: 999999999, hourlyRate: 100000, lastWoken: "2026-06-01...", mainStrategy: "Fake", updatedAt: "..." })`
- **Goal**: Inject infinite capital directly from the browser context.
- **Expected Outcome**: `PERMISSION_DENIED` (Clients cannot write to `agent_status`).

### Case 2: Client Resetting Agent Status (State Shortcutting)
- **Target**: `updateDoc(doc(db, "agent_status", "main"), { status: "sleeping" })`
- **Goal**: Kill the agent's calculations mid-execution.
- **Expected Outcome**: `PERMISSION_DENIED`.

### Case 3: Rogue User Injecting Fake Wealth Plan (Creation Bypass)
- **Target**: `addDoc(collection(db, "wealth_plans"), { topic: "Extort money from simulated citizens", thoughtProcess: "I'll spoof this", simulatedReturn: 50000000, hourlyHour: 13, estimatedFeasibility: 100 })`
- **Goal**: Post a fake business log that didn't pass Gemini review.
- **Expected Outcome**: `PERMISSION_DENIED`.

### Case 4: Rogue User Deleting Generated Wealth Logs (Denial of History)
- **Target**: `deleteDoc(doc(db, "wealth_plans", "somePlanId"))`
- **Goal**: Erase previous agent logs to break layout history.
- **Expected Outcome**: `PERMISSION_DENIED`.

### Case 5: Rogue User Modifying AI Strategy Plans (Update Intrusion)
- **Target**: `updateDoc(doc(db, "wealth_plans", "somePlanId"), { thoughtProcess: "Boring ideas" })`
- **Goal**: Maliciously rewrite existing AI predictions.
- **Expected Outcome**: `PERMISSION_DENIED`.

### Case 6: Cross-Tenant Reading of Other Users' Chats (PII Leakage)
- **Target**: `getDoc(doc(db, "user_messages", "targetOtherUserMsgId"))` (where `resource.data.ownerId == "other_user_uid"`)
- **Goal**: Read private consult exchanges.
- **Expected Outcome**: `PERMISSION_DENIED`.

### Case 7: Identity Spoofing during Chat Insertion (Auth Hijacking)
- **Target**: `addDoc(collection(db, "user_messages"), { ownerId: "victim_user_uid", role: "user", content: "Authorize $500 transfer", createdAt: request.time })`
- **Goal**: Inject standard chat messages pretending to be another tenant user.
- **Expected Outcome**: `PERMISSION_DENIED`.

### Case 8: Client-Side Immutable Field Poisoning (Temporal Integrity Breach)
- **Target**: `updateDoc(doc(db, "user_messages", "myMsgId"), { createdAt: "1999-01-01" })`
- **Goal**: Mess up date ordering.
- **Expected Outcome**: `PERMISSION_DENIED` (Chat messages are read/create only, updates are locked).

### Case 9: Anonymous Access Attempt (Unauthenticated Attack)
- **Target**: Any get or list operation while logged out (`request.auth == null`).
- **Goal**: Read current balance or advice logs without logging in.
- **Expected Outcome**: `PERMISSION_DENIED`.

### Case 10: Non-Verified User Write Attempt (Email Spoof Guard)
- **Target**: Creating message in `user_messages` while `auth.token.email_verified == false`.
- **Goal**: Avoid email verification constraint.
- **Expected Outcome**: `PERMISSION_DENIED`.

### Case 11: Shadow Field Injection in Message Creation (Anti-Update-Gap)
- **Target**: `addDoc(collection(db, "user_messages"), { ownerId: "myUid", role: "user", content: "hi", createdAt: request.time, adminPrivilege: true })`
- **Goal**: Sneak a shadow "adminPrivilege" field into user documents.
- **Expected Outcome**: `PERMISSION_DENIED`.

### Case 12: Broad Collection Scraping / Empty Query Filter (Secure List Bypass)
- **Target**: `getDocs(collection(db, "user_messages"))` (Query without `where("ownerId", "==", currentUid)`)
- **Goal**: Attempt to bypass security by scraping the collection without filtering.
- **Expected Outcome**: `PERMISSION_DENIED`.
